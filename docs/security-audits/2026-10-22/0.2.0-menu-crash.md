# Kumo 0.2.0 toolbar menu crash

The installed 0.2.0 build `202610210004` crashed while constructing the toolbar
app menu, before the Settings page was opened. The October 22 report identifies
`tab_groups::STGEverythingMenu::ShouldEnableCommand(int)` with a null receiver,
command argument `65002` and an invalid read at address `0x88`.

Kumo's native integration assigned its static Agent Connections command `65002`
and Check for Updates command `65001`. Chromium reserves IDs starting at
`COMMAND_ID_FIRST_UNBOUNDED` (`0xE000`, 57344) for dynamic menu items. The app menu
classifies those commands before consulting the normal browser command model.
With five dynamic menu types, the two IDs resolve to tab groups and other
profiles, respectively. The tab-group delegate has not been constructed when
the static Kumo item is added, causing the reported null dereference.

The source overlay now assigns unused bounded IDs `56000` and `56001`, retaining
the existing command handlers and enabled-state checks. A preprocessing guard
rejects either command if it enters the dynamic range in a future edit.
Chromium's dynamic menu dispatch and its security checks are unchanged.

Two regressions cover the generated header:

- Both product commands must be distinct, bounded and free of numeric aliases
  with upstream commands. This failed for both original IDs before the fix.
- Clang preprocesses the actual generated guard with Chromium's command-range
  header. The corrected IDs pass; moving either command back to `65002` fails.

The original overlay suite passed all 20 tests after adding the first regression;
the additional Clang regression also passed. The incremental build replays all
98 native overlay outputs against the pinned pre-overlay source and changes only
`chrome/app/chrome_command_ids.h` plus its preparation manifest. Its input digest
is `aed76d059e2f9c5313847592f8b36a74eb8866200f1f7f890fe4e442437e81ea`.
The old build receipt was preserved and invalidated in the build workspace;
completed-build status must come from the ordinary build driver.

Build and runtime results are recorded in
`.cache/qa/settings-menu-crash-20261022/`. The published 0.2.0 artifacts have not
been modified. Opening `chrome://settings/kumo` directly bypasses the failing
menu in that release.

## Patched build qualification

The ordinary incremental build completed successfully at `2026-10-22T17:34:38Z`.
Its completed receipt is
`6fa08144fc83fe9c5f1aea78b90608cd7e9a6bc44ed192e7cff91e83775e9982`.
Normal packaging of 0.2.1 build `202610220001` passed signature, engine startup,
helper startup and development-updater status checks.

The original 0.2.0 QA binary reproduced the same null-receiver crash with command
65002 in a disposable profile. The patched packaged binary opened the toolbar
menu repeatedly, activated Settings, navigated from New Tab to native Settings
through Agent Connections, and launched the expected updater executable through
Check for Updates. The development updater does not perform a production update;
its separate window inspection timed out. Its owned process was terminated after
checking its exact executable path. The browser quit through its application menu
with exit code zero, and the packaged resource seal remained unchanged.

Before the baseline test, selecting the QA application too early auto-launched
its normal-profile picker. No profile was selected; that instance was closed,
the error was disclosed, and both actual regression runs used disposable profiles.
The installed `/Applications/Kumo.app` was not replaced by this qualification.

Release signing, notarization and publication are subsequent gates; these local
QA results do not claim Apple acceptance or public availability.
