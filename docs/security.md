# Security controls and remaining work

App-update delivery uses [signed Kumo GitHub Releases](github-releases.md) through a separate native Sparkle companion. Published production releases have Developer ID signatures and Apple notarization; Apple Development packages disable update network checks. Every replacement still requires the selected identity, notarization, update-signing key and reviewed source commit.

The pending **0.1.2, build 202610210003** removes Kumo's built-in Apple Passwords sheet, settings, pairing components and SDK probes. Ordinary extension/Native Messaging support and Chromium WebAuthn remain. Compatibility with the owner's custom password plugin or Apple's helper is not established. The unpublished 202610210002 candidate is superseded; its acceptance and tests do not qualify the changed binary. A fresh completed build, validation and notarization remain required. Widevine is absent, and the reported Crunchyroll issue remains unresolved.

## Optional domain protection with Quad9

Chromium's native Secure DNS controls offer a way to add an independent threat-blocking resolver. Quad9's recommended public endpoint is `https://dns.quad9.net/dns-query`; it combines malware-domain blocking with DNSSEC validation. It does not require an account or API key. DNS queries go to the selected resolver. See [Quad9's service addresses](https://quad9.net/service/service-addresses-and-features/).

To configure it yourself, open Kumo's native Settings → Privacy and security → Security, turn on **Use secure DNS**, select the custom provider option, and enter that endpoint. The first .84 source package's `smoke-dns.mjs` selected it through native Settings, completed Chromium's real DNS probe, and verified that strict secure mode and the template survived a restart in a disposable profile. Managed-device and parental-control policies can affect availability. Chromium's explicit secure mode fails DNS resolution when the resolver is unavailable; automatic mode may fall back to insecure DNS. These modes are defined in Chromium's [DNS-over-HTTPS policy](https://chromium.googlesource.com/chromium/src/+/main/components/policy/resources/templates/policy_definitions/Miscellaneous/DnsOverHttpsMode.yaml).

Use [Quad9's browser verification page](https://on.quad9.net/) after configuring the native setting. Quad9 documents its verification and block diagnostics in its [FAQ](https://docs.quad9.net/FAQs/). Kumo does not modify your system DNS settings or install this configuration automatically.

This is domain-level protection. It cannot inspect a malicious path on an otherwise allowed domain, provide a download-file reputation verdict, or cover connections that do not resolve through that resolver. It does not replace Safe Browsing's URL and download checks. Quad9 explains the scope of its [threat blocking](https://quad9.net/service/threat-blocking/).

## Reputation feeds and signed updates

A maintained reputation integration needs a provider agreement and a reliable update path. [URLhaus](https://urlhaus.abuse.ch/api/) requires an Auth-Key and notes that commercial use may require a paid subscription; its scope is malware distribution, rather than phishing generally. [OpenPhish's community feed](https://openphish.com/phishing_feeds.html) is limited and updates every 12 hours, and its [terms](https://openphish.com/terms.html) restrict product/commercial use and redistribution without written consent. Kumo does not bundle either feed or submit visited URLs to them.

The native Kumo updater uses the owned GitHub Releases endpoint, signed feeds and archives, and a distinct increasing Kumo build number. A separate Sparkle companion remains alive while the Swift browser bootstrap replaces itself with Chromium using `execv`. The companion coordinates closed browser profiles before installation. Update-signing keys are separate from Apple's Developer ID identity. Development packages keep update checks disabled; production packages require Developer ID signing and successful notarization before public assets are prepared. Each changed release needs its own validation; earlier installation or signature evidence does not qualify the pending replacement.
